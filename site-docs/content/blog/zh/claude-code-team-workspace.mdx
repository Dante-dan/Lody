“Claude Code 团队”这个说法，实际指着两件不同的事。

一件是计费安排：套餐里的席位、一张发票、一个能加人减人的管理员。它回答的是*谁可以用这个 CLI、谁付 token 的钱*。

另一件才是工程师在密集用 Agent 两周后真正会去搜的东西：一个地方，**能同时跑好几条编程 Agent**，同事**看得到**在跑什么，而且别人**能接手**一条做了一半的会话。套餐回答不了这个——CLI 会话活在一个终端、一份工作副本、一台笔记本里。

这篇讲的是后者：一个多模型编程 Agent 工作空间到底怎么搭起来。以 [Lody](https://lody.ai) 作为具体实现，讲底下的机制、准确的设置路径，以及真正会硌到人的地方。

## Lody 工作空间不是 Anthropic 的 Claude Code Team 套餐

这点得说白，因为搜索结果里它们是糊在一起的。Lody 不转售 Anthropic 席位，不代理你的 token，也不是只能用 Claude。Claude Code 只是你在会话里可以选的**一种** [Agent Config](/zh/docs/agents)，旁边还有 Codex、Kimi Code、DeepSeek Harness，以及 [ACP Registry](/zh/docs/cli-runtimes) 里的任何运行时。凭据还留在原来的位置：跑 Lody CLI 那台机器上的订阅登录，或者你粘进配置里的 API Key。

三个层，经常被压成一个问题：

| 层 | 它负责什么 | 它从来不负责什么 |
| --- | --- | --- |
| 厂商套餐（Anthropic、OpenAI、月之暗面、DeepSeek……） | 席位、限流窗口、账单、模型权限 | 会话跑在哪里、谁还能打开它 |
| 编程 CLI（Claude Code、Codex、Kimi Code……） | 一段对话、一个工作目录、一个终端 | 并发任务之间的隔离、团队可见性、交接 |
| 工作空间（Lody） | 会话、Worktree、机器、成员、可见性 | 卖 token，或替掉你的 CLI |

把这三层分清，“Claude Code 能不能做团队”这类混乱基本就散了：它可以挂在团队*套餐*上；团队共用的那块会话面板是另一层，得你自己带。

## 四种协作形态，以及各自用错的样子

真实的多 Agent 用法基本落在四种形态里。选错形态，就是“几个 Agent 互相打架”和“我又得把需求重讲一遍”的常见来源。

| 形态 | 隔离的部分 | 共享的部分 | 什么时候用 | 什么时候会翻车 |
| --- | --- | --- | --- | --- |
| **并行会话** —— 主页开多条对话 | 各自的 Worktree、分支、对话 | 仓库历史、机器 | 工作项彼此独立，每项对应一个 PR | 两项动同一批文件，还各自从旧基线开 PR |
| **子标签 / 侧边对话** —— 一条会话里的额外对话 | 各自的对话历史 | **同一个工作目录** | 审阅或追问主标签正在产出的改动 | 你把它当隔离用——它不是，两边看得见彼此的改动 |
| **交接** —— 同事接着你的会话做 | 什么都不隔离，这就是重点 | 对话、Diff、Worktree、分支 | 上下文很贵，而活还没干完 | 两个人同时去引导同一个正在跑的 turn，还没说好谁开车 |
| **委派分发** —— 一个 Agent 驱动其他会话 | 各自的 Worktree | 发起的那条对话保留关系 | 一条提示词应该拆成若干专注对话，再汇总回来 | 你指望它是后台调度器；它的范围只限 Lody 自己的对话数据 |

最容易被搞错的是第二行。[子标签](/zh/docs/session-tabs)会继承父会话的机器、项目或仓库、分支、Agent Config、模型和权限默认值，并保留自己的历史——但它在**同一个目录**里干活。右侧栏的**侧边对话**同理。它们是审阅面，不是沙箱。隔离只来自拥有独立 [Worktree](/zh/docs/worktrees) 的会话（或 **新 Worktree** Fork）。

## 隔离靠的是一个目录，不是一句承诺

并行 Agent 能共存，原因既无聊又物理：每条会话都有自己的检出。

会话使用 Worktree 时——GitHub 会话总会用，[本地项目](/zh/docs/local-project)可选——Lody 会新建分支（默认 `session/<shortSessionId>`），把它检出到 `~/.lody/repos/<repoId>/worktrees/<sessionId>/`，运行项目的 setup 脚本，然后才把第一条提示词交给 Agent。Git 历史通过一个 bare 仓库共享；工作文件完全不共享。

由此产生两个结论，它们决定五个 Agent 一起跑是舒服还是难受：

**1. setup 脚本就是你的并发预算。** 它在 Worktree 建好之后、第一条提示词之*前*运行，所以 N 条会话就会执行 N 次。每个 Worktree 里直接 `pnpm install`，磁盘上就是 N 份 `node_modules`。把包管理器指向共享 store 或缓存，并把清理放进 cleanup 脚本——它在会话归档时、目录被删除之前运行。两个脚本都在 **设置 → 项目** 的 **Worktree setup** / **Worktree cleanup** 里。

**2. 文件隔离了，端口和数据库没有。** 五个 Agent 各跑一个 `pnpm dev` 抢 3000 端口，即使文件互不相干也会撞。Lody 会给这两个脚本注入 `LODY_SESSION_ID`、`LODY_WORKTREE_PATH`、`LODY_WORKTREE_BRANCH`、`LODY_WORKTREE_SCRIPT_PHASE`，以及 `LODY_GITHUB_REPO` 或 `LODY_LOCAL_PROJECT_ID`——所以按会话 ID 派生这类资源，别写死：

```bash
# Worktree setup：给每条会话自己的端口和库名。
offset=$(( $(printf '%s' "$LODY_SESSION_ID" | cksum | cut -d' ' -f1) % 900 ))
echo "PORT=$((4000 + offset))" >> .env.local
echo "DATABASE_URL=postgres://localhost/app_${LODY_SESSION_ID:0:8}" >> .env.local
```

脚本里 export 的变量只在该脚本进程内有效。**Agent** 本身需要的环境变量应该写在 [Agent Config](/zh/docs/agents) 里。

归档会话时，Lody 会先把未提交的改动提交到该分支，再删掉 Worktree 目录回收磁盘；对话和分支都留着，恢复会话时 Worktree 会重建。所以“合并即归档”是并行任务的自然收尾——**设置 → 通用** 里有 PR 关联会话的自动归档规则。

## “多模型”其实是两种不同机制

这一层是多数对比文章会抹平的。在 Lody 里，Agent Config 是 **CLI 类型 + 环境变量**，因此“跑 DeepSeek”可以是结构上完全不同的两件事：

- **同一个 CLI，换一个端点。** `ANTHROPIC_BASE_URL` / `ANTHROPIC_MODEL` 这类预设——*DeepSeek over Claude Code*、*GLM over Claude Code*、*MiniMax over Claude Code*、*MiMo over Claude Code*，以及走 Claude 兼容端点的 Kimi 或 Qwen——跑的都是 Claude Code 这个可执行文件，只是打到别家的 Anthropic 兼容 API 上。工具面一样，权重和账单不一样。
- **换成真正不同的运行时。** Codex、**Kimi Code**（由 Lody 托管运行时，你不用自己装命令）、**DeepSeek Harness**（内置 ACP 提供方，用 `DEEPSEEK_BASE_URL` / `DEEPSEEK_API_KEY`，不需要独立的 `dsh`）、[ACP Registry](/zh/docs/cli-runtimes) 里的任意条目，或者用自己的 stdio 启动命令走 **Custom ACP**。

这个区别在运维上为什么重要：**能力是按配置探测出来的，不是假设出来的。** 你在 **设置 → Agent 配置** 里点 **Test**（或在那台机器上执行 `lody agent-config refresh-capabilities <idOrName>`）时，Lody 会读取运行时声明的能力，之后对话界面只暴露它真正支持的东西。具体地：

- **Fork**，以及依赖它的**侧边对话**，只在当前 Agent 声明原生会话 Fork 时才出现。不支持的运行时当不了你“分出一条审阅线”的那个角色。
- 斜杠命令来自能力探测，所以 `/review`、`/compact` 是否存在，取决于配置和已安装版本。
- **Fast Mode** 只在所选配置声明该选项时出现；提示文案会写明代价（大约快 2.5 倍，单 token 成本更高）。
- **Steer**——不取消当前任务、直接改方向——在 Claude Code 和 Codex 上可用：在 **设置 → 通用** 里把 **排队消息行为** 设成让排队消息去引导当前 turn，或在第一条排队消息上选 **引导**。

所以搭混合阵容时，有用的问题不是“哪个模型更聪明”，而是：*就它在我的流程里占的那个位置而言，它声明的控制能力够不够用？* 实现型 Agent 需要 Steer 和斜杠命令；审阅型 Agent 会吃到 Fork 的好处；批处理型两个都不需要。

### 真正的并发上限是限流，不是 CPU

阵容规模受三件事约束，按顺序是：订阅的限流窗口、宿主机的 CPU / 内存 / 磁盘，以及一个人实际能审多少条对话。第一件在撞上之前是看不见的——**设置 → Agent 配置 → 机器** 会显示受支持订阅窗口（例如 5 小时和 7 天）的剩余额度与刷新时间。

由此得到的实用安排：把订阅配置留给你正在盯着引导的那条深度会话，把并行的宽度放到按量计费的 API Key 配置上，让一次爆发只是花钱，而不是把你的主力工具堵死。Lody 不会替你在多个配置之间做负载均衡——是你按会话选的，这也正是花两分钟把这套选择存成 Role 划算的原因。

事后归因在 **设置 → AI 用量** 里，包含 **按成员** 的拆分。

## 让配置可复现：Agent Role

团队真正的问题不是开起一个 Agent，而是“审阅用的那套配置”只存在于某一个人的脑子里。[Agent Role](/zh/docs/agent-roles) 会把整套东西钉住——机器、Agent Config、模型、推理档位、权限模式，以及可选的默认指令——收进一个名字，之后在输入框的 **Role** 一行点一下，或用 `@` 提及它来开一条**新**对话。

让 Role 值得信任、而不是又一层间接的地方在于：

- 一个 Role **精确绑定一台机器和一个 Agent Config**，绝不悄悄换成别的。它的机器离线或配置被删时，Role 仍会列在那里、标出准确原因，并且拒绝运行。不会静默降级到另一个模型上——而你的审阅标准本来是按某个模型设的。
- 它**不存 API Key，也不存 MCP 选择**——那些留在 Agent Config 里。
- 你提及它那一刻它是什么样，会被**冻结进那次请求**，所以之后编辑或删除 Role，都改不了已经被接受的工作。
- **与工作空间共享** 让它对所有成员可见、可提及、可运行；它仍然跑在自己那台机器上，所以成员需要有这台机器的访问权。

依赖它之前值得知道的两个行为：在已经创建的对话里，Role 一行只应用运行配置——Role 的默认指令**不会**追加进去，而且只提供绑定同类型 Agent 的 Role。另外，你一旦手改模型，输入框底部就会去掉 Role 的名字，因为它不会声称一个并非将要运行的 Role。

## 可见性的单位是机器，不是会话

这是邀请任何人之前最该先想通的一件事。你注册的每台机器**默认私有**；加入工作空间不会暴露你的笔记本，而且只有机器的所有者能改共享状态。未共享机器上的会话根本不会同步到其他成员的侧边栏——而在会话上点 **Share with team…** 可能会把底层机器（本地项目会话还包括该项目）共享给整个工作空间，这台设备上*其他*对话也可能因此可见。确认框会先说明范围。

由此得出的架构选择：如果你想要稳定的团队可见性，又不想把每个人的笔记本都公开，就把需要团队可见的活跑在一台**专用共享机器**上。任何服务器通过 SSH 跑 CLI 就能加入工作空间：

```bash
# 在共享机器上。Token 来自 设置 → 账号 → CLI Token。
lody login --auth "$LODY_AUTH" --machine-name team-runner
lody daemon start
```

然后在 **设置 → 机器** 里对这一台打开 **共享机器**，笔记本保持私有。成员建会话时选这台共享机器；主页侧边栏筛选（默认 **全部任务**，另有 **我的任务**，移动端是 **团队任务**）会显示谁在跑什么，每条会话都有头像。

之后交接到一条现场会话就是两分钟的事：在 **设置 → 工作区 → 通用** 的 **成员** 里 **邀请成员**，把会话变成团队可见，然后让对方打开*那一条*会话，而不是 Fork 它。完整的权限面和边界情况见[共享并交接 Agent 会话](/zh/docs/session-handoff)。

有一条协作规则产品替你管不了：共享会话没有“唯一司机”，所以要说好下一条提示词由谁发。交接搬走的是上下文，不是锁。

### 第一个小时该按什么顺序配

1. **设置 → 机器** —— 先定哪台机器承载需要团队可见的活，把它登记进来（不是笔记本的话，在服务器上跑 `lody daemon start`），然后只共享这一台。
2. **设置 → 工作区 → 通用** 的 **成员** → **邀请成员** —— 成员身份是前提，没有它后面什么都碰不到。
3. **设置 → Agent 配置** —— 每个*凭据来源*一个配置，逐个点 **Test** 把能力缓存下来。命名按钱从哪来（`claude-sub`、`deepseek-api`），不要按任务命名。
4. **设置 → Agent 角色** —— 把你真正会重复的那两三套配置收成 Role，再 **与工作空间共享**，让同事跑的和你一样。
5. **设置 → 项目** 的 **Worktree setup** / **Worktree cleanup** —— 在开五个 Agent *之前*就把 N 份检出做便宜、把每条会话的端口做唯一，而不是之后。
6. **设置 → 通用** —— 排队消息行为，以及 PR 关联会话的自动归档，让干完的并行活自己从侧边栏消失。

## 不想手点时：脚本化分发

对可复制的批量活——把一条 lint 规则铺到所有包、给每个服务升同一个依赖、在二十个文件上做同一处重构——[CLI](/zh/docs/cli) 比在输入框里点二十次更合适。对 GitHub 仓库执行 `lody session create`，会像 UI 会话一样拿到自己的 Worktree 和分支（本地项目要用 `--worktree` 显式要一个），隔离模型完全一致：

```bash
# 一个工作项一条会话，交替使用配置以分摊额度。
i=0
while IFS= read -r task; do
  config=$([ $((i % 2)) -eq 0 ] && echo claude-sub || echo deepseek-api)
  lody session create \
    --workspace my-team \
    --repo owner/repo \
    --branch main \
    --agent-config "$config" \
    "$task"
  i=$((i + 1))
done < tasks.txt

lody session list --workspace my-team --json |
  jq -r '.sessions[] | "\(.id)  \(.status.type // "unknown")  \(.title // "untitled")"'
```

不知道会被绊一下的前提条件：`session create`、`session chat`、`session cancel` 需要那台机器上有 `lody start` 或 `lody daemon start` 在跑，而 `list` / `show` / `history` 只需要登录；`--repo` 和 `--local-project` 互斥；`--mode` 和 `--model` 会覆盖 ACP 选择；派活之前想确认某台机器实际能跑什么，用 `lody machine list --json --include-acp-capabilities`。

如果你想让**一个 Agent** 去做拆分并汇总回来，那是 [Agent 对话控制](/zh/docs/session-orchestration)——需要打开 **开发者模式** 和 **Tasks** beta（**设置 → 关于**）。需要判断力的拆分用它；任务清单已经确定、还想放进 CI 的，用 CLI。

## 怎么选

**用一个模型还是好几个？**

- 一个配置、多条会话：默认答案。工具面一致，额度池只有一个，最好推理。
- 拆配置的时机是：撞上了限流窗口；单 token 成本值得把并行宽度挪出订阅；或者流程里某个位置需要的能力，别的运行时并不声明。
- 不要为了“再要一个意见”而在同一时间对同一文件拆配置。两个 Agent 改一个工作目录，正是那种撞车场景；给第二个自己的会话，让它读 Diff。

**并行还是交接？**

- 活是**新的**且相互独立时并行——一项、一条会话、一个 PR。
- 活**没干完**、而最贵的部分是 Agent 已经吃进去的上下文时，交接。
- 想对当下正在发生的改动换个角度看、并且接受共享文件时，用子标签。
- 拆分本身需要判断力、结果又该回到一条主线上时，用委派分发。

## 老实说的边界

- 可见性以机器为单位（加上本地项目授权）。没有按会话的白名单，共享一条会话可能连带放大同一设备上的其他对话。
- 对话控制的范围被刻意限制在 Lody 自己的对话数据里——它不是通用后台调度器。被委派的任务可能在超时之后才结束；即便发起方已经拿到超时结果，产出仍留在那条对话里。
- Claude Code 的后台任务面板只报进度，不能从里面取消单个后台任务；定时任务面板是只读的。
- `/compact` 能执行，但 Lody 目前不渲染随之而来的更新，所以你不会看到这条命令的 Agent 回复。
- DeepSeek Harness 有一个已知的上游继承限制：会话模型不是 `DeepSeek-V4-Pro` 时，被委派的子 Agent 仍可能沿用创建时的 `DeepSeek-V4-Pro` 种子，可能推高用量成本。
- Role 不带密钥、不带 MCP 选择，也没有 Role 级别的自动批准策略；权限是被钉住的一个运行配置值，不是团队策略引擎。
- 本地（非 GitHub）项目支持聊天、文件列表、Diff 审阅、移动端和预览，但没有 PR 与 CI 自动化。
- 已归档的会话，其对话历史和 Git 分支仍留在机器上，直到你删除它们——并行干活还是需要定期清理。

## 常见问题

### Lody 工作空间和 Claude Code Team 套餐是一回事吗？

不是。厂商套餐管的是某个 CLI 的席位、额度和账单。Lody 工作空间管的是会话、Worktree、机器，以及谁能看到或接着做。两者可以只用其一，也可以都用；Lody 直接用机器上已有的订阅登录，或者用 Agent Config 里的 API Key。

### 团队里每个人都要装 Claude Code 才能共用工作空间吗？

不需要。会话跑在承载 Lody CLI 和凭据的那台机器上，所以打开共享会话的同事，驱动的是*那台*机器上的运行时。他需要的是工作空间成员身份，加上会话所用机器（以及本地项目，如有）的访问权。

### 并行几个 Agent 比较合适？

真正卡住的通常是审阅带宽，不是算力：一个 PR 粒度的工作项一条会话，同时开着的不要多于你能看完 Diff 的数量。在那之前，先看 **设置 → Agent 配置 → 机器** 里订阅的限流窗口，以及磁盘余量——每个 Worktree 都是一份真实检出，带真实的构建产物。

### 两个 Agent 能同时在一个仓库里干活而不冲突吗？

各自有 Worktree 时可以——分开的会话，或 **新 Worktree** Fork。它们只共享 Git 历史，别的都不共享，未提交的改动留在产出它的那条任务里。**当前工作区** Fork、侧边对话和子标签是有意共用源目录的，能看见彼此的改动。

### Agent 干到一半时，同事能接手吗？

可以打开这条会话接着做——同一段对话、Diff、Worktree 和分支。但要说好谁开车：交接转移的是上下文，不是独占权。turn 正在跑时发出的消息会进队列，它是引导当前 turn 还是等着，取决于发送者的排队消息行为设置。

### 共享一条会话会把我整台笔记本暴露出去吗？

它可能让这台机器上的其他对话可见，所以确认框会在你确认前说明范围。机器在所有者主动共享之前都是私有的，之后也可以在 **设置 → 机器** 里把 **共享机器** 关掉。如果想让 Agent 的活长期对团队可见，把它放到专用共享机器上，而不是个人机器上。
