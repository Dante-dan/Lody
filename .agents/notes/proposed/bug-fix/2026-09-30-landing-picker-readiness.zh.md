# 可选机器就绪后解除 landing 选择器等待

Status: proposed
Translation: current

[English](2026-09-30-landing-picker-readiness.md) | 中文

## 摘要

已有可访问机器及其 agent 配置时，landing 选择器仍会等待整个文档元数据缓存，使冷启动等待超过选择操作实际所需的数据范围。此修复让文档缓存加载与可见性加载采用相同判断：仅在没有可选机器时阻止选择。运行时初始化与本地机器首次探测仍是前提，默认选项恢复也保留独立的元数据门槛。这是等待上游审查的参考实现，尚未测量原始 Windows 启动场景。

## 决策与证据

[Issue #496](https://github.com/LodyAI/Lody/issues/496) 将选择器条件与[已关闭且未合并的 PR #317](https://github.com/LodyAI/Lody/pull/317) 中较大的移动端同步改动分开。历史补丁只是参考，不表示方案已被采纳或仍有实际实施负责人；关闭记录没有明确拒绝原因。

`getChatLandingInitialDataLoading` 原先因文档缓存未完成而提前返回，绕过了可见性加载已有的可选机器例外。将此例外同时用于两种加载状态，并保留运行时与首次本地探测检查，避免缓存机器绕过启动前提。`useChatLandingDefaults` 中的文档缓存检查保持不变，防止元数据尚未到达时提前结束恢复或覆盖已存选择。

继续等待整个缓存会保留所报告的选择器延迟；无条件移除缓存检查则会提前显示误导性的空状态提示。所选条件同时避免两者：没有可选机器时仍等待缓存和可见性查询。

## 验证与限制

扩展已有派生状态测试，覆盖两种可见性加载状态下已有可选机器的情况，以及无机器时元数据由未就绪转为就绪的过程。该测试套件与已有默认选项套件共 94 项通过；`pnpm format` 与 `pnpm run docs check` 通过。这是代码层回归验证，不表示 Windows 桌面复现或启动时间测量；没有修改 Spec 意图或批准状态。
