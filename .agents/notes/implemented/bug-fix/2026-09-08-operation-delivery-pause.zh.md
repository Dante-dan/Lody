# 停止后将操作结果留到下一条用户输入

Status: implemented
Translation: pending

## 摘要

停止过去只取消当前回合，已积压的不同操作仍会逐条续聊。现在用户停止会持久标记旧操作及其来源，重启和迟到完成都不会解除阻挡。下一条看到当前停止版本的用户消息会一次携带已就绪结果；旧排队消息、自动重试和新任务的正常续聊有独立处理。界面显示当前请求者的待处理数量，支持本次不携带或手动处理；运行时与数据库测试已执行，安装包验收和跨机器迁移不在本次验证范围内。

## 依据与决策

基线 `3772961c` 的 coordinator 使用每会话 Promise 链逐条执行 Delivery，`cancelSession` 只取消精确匹配的回合。现有执行认领防止单条重复执行，但无法阻止不同通知在停止后继续启动。编辑并重发、MCP 单操作取消也经过取消路径，所以只给用户 Stop 增加持久阻挡；内部取消通过 `--turn-only` 保留原义。

行为见 [草案](../../../../specs/operation-delivery-control.zh.md)，实现职责与兼容边界见 [编排 README](../../../../apps/cli/src/orchestration/README.md#deferred-results)。这是现有逐操作执行认领之上的补充，不改变委派深度限制或目标任务生命周期。

早期提案要求额外点击恢复。改为下一条用户输入携带结果，避免用户补充指令时还需切换状态；同时不重新放开整条旧队列。旧操作的迟到结果继续等待，新来源回合发起的工作仍自动续聊。

## 持久边界

- SQLite 侧表保存停止来源、持有的操作、停止版本和用户输入收据。停止与接受操作均在立即写事务中完成，插入触发器覆盖停止后的迟到接受和旧完成回合的后续操作。
- UI 在发送时冻结停止版本及携带选择。队列提升、普通 dispatch 和 steer 保留它们；输入版本与当前停止版本不一致时不携带结果，避免已有队列代替用户的下一次主动输入。
- provider 调用前同步认领结果并记录 started；一个用户输入只有一个收据，claim 使用随机标识防止旧拒绝回调释放新尝试。确认 steer 未提交时释放；取消已开始输入不重放；未知结果保留 uncertain。
- 结算失败保留确切结果并安排仅结算重试，不再次调用代理。暂停写失败时保留进程内门禁、取消当前回合并返回失败，不能宣称重启后仍有效。
- 已有 progress 卡片独立更新；暂停不追加 completion 回合。元数据只投影版本和按请求者计数，跳过相同值，不能作为执行权来源。

## 输入与兼容性

输入使用当前用户的模型与指令，旧结果明确标为参考资料。较大积压保留结构、目标历史引用和截断信息，每次最多 68 KiB；仍放不下的结果保留待处理，不能自动拆成多轮。原始操作结果继续保存在数据库，已消费结果沿用七天保留策略，未消费暂停结果不因自动投递过期规则而消失。

新协议声明 `deferredOperationInputs` v1。内部 CLI 取消仅在目标支持时发送 `turnOnly` 字段，旧守护进程仍收到原来的 payload。旧客户端没有停止版本，因此不能排空新守护进程的暂停结果；需要支持本协议的客户端发送新消息。持久保证限于同一机器的重启，降级旧二进制或跨机器迁移不会自动继承执行门禁。
